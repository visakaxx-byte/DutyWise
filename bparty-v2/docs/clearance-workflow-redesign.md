# 清关生成工作流重构方案

日期：2026-06-01

## 背景

服务器任务 `CMDUCHN3357475` 暴露出当前流程的核心问题：客户清单很杂乱，但系统没有先对客户清单做归纳，也没有把归纳后的客户品类作为主候选池。当前流程主要保留提单品名，再用替换清单补足行数，导致输出品名、数量、重量、单价和货值都可能偏离客户资料。

该任务的关键证据：

- 清单有 185 行、75 个品类，原始货值 182,859.56 USD。
- 提单品名只有 `PLASTIC HAIRPIN` 和 `PLASTIC KEYCHAIN`。
- 输出 10 行中只有 2 行来自提单，其余 8 行来自替换清单。
- 输出总货值 5,882.30 USD，仅为原始货值的约 3.22%。
- 输出所有行都有重量合理性警告，多数是毛重被强制倒推后单件重量不合理。

## 目标

新流程需要满足四个原则：

1. 先理解客户清单，再生成清关输出。
2. 输出品名优先来自整理归纳后的客户清单，替换清单只作为兜底。
3. 总重量闭合的同时，每个品类的单件重量、单箱重量也必须符合常识。
4. 单价和货值要有外部价格依据，默认按电商零售价均值的 30% 估算申报单价。

## 新工作流

### 1. 输入解析

输入包括客户清单 Excel 和提单 PDF。

清单解析字段：

- 中文品名
- 英文品名
- HS 编码
- 材质
- 用途
- 箱数
- 数量
- 单价
- 总价/货值
- 净重
- 毛重

提单解析字段：

- 提单号
- 提单品名
- 总箱数
- 总毛重
- 发货人/收货人
- ETA

解析阶段只负责抽取事实，不做低报优化。

### 2. 清单归纳

客户清单经常存在多语言混写、重复品名、细项拆分、HS 粘连和行级数据缺失。需要先由大模型做一次标准化归纳。

归纳输出必须是结构化 JSON，不允许自由文本：

```json
{
  "groups": [
    {
      "normalized_name_zh": "塑料发饰",
      "normalized_name_en": "Plastic hair accessories",
      "source_rows": [49, 62, 75],
      "source_names": ["假发发夹", "塑料发饰", "夹子"],
      "material": "Plastic/Fiber",
      "usage": "Hair accessory",
      "hs_candidates": ["9615900000", "9615115000"],
      "total_ctns": 0,
      "total_qty": 18,
      "total_weight": 0,
      "total_value": 90,
      "confidence": 0.86,
      "notes": "清单中存在发夹、发饰、夹子等相近品名，归并为发饰类。"
    }
  ],
  "warnings": [
    {
      "type": "bad_hs",
      "rows": [28],
      "message": "HS 编码疑似多个编码粘连。"
    }
  ]
}
```

归纳结果要作为后续候选池的主数据源。

### 3. 候选品名选择

候选选择顺序：

1. 从清单归纳池选择符合提单品名、税率、认证、重量和价格要求的品类。
2. 提单品名必须覆盖，但优先映射到清单归纳池中的相近品类。
3. 清单归纳池不足时，才从替换清单补充。

替换清单使用规则：

- 替换品行数默认不超过最终输出行数的 20%-30%。
- 替换品必须有替换原因，例如认证风险、HS 不可用、客户清单没有足够合规品类。
- 替换品不能与客户清单语义完全无关。
- 替换品不能为了降低税率强行引入高价值或高重量品类。

### 4. HS 编码确认

每个候选都需要查询 codeflagai 或等价 HS 数据源。

输出字段：

- 原始清单 HS
- 提单/品名查询 HS
- 推荐采用 HS
- 爬虫匹配品名
- 基础税率
- 加征税率
- 认证要求
- 采用原因
- 风险提示

硬规则：

- 禁止只因低税率选择语义不匹配的编码。
- 清单 HS、查询 HS 和替换清单 HS 冲突时，必须进入冲突解释。
- 爬虫品名与输出品名明显不一致时，候选不能直接通过。
- 多个 HS 粘连的清单行必须先拆分或标记为不可直接采用。

### 5. 重量规划

总重量来源优先级：

1. 客户明确要求使用提单毛重时，最终输出总毛重必须对齐提单毛重。
2. 提单未识别到毛重时，使用清单可验证的总毛重。
3. 清单和提单重量差异过大时，进入异常说明，不直接生成。

每个品类还需要由大模型给出合理重量范围：

```json
{
  "normalized_name": "Plastic hairpin",
  "kg_per_piece_min": 0.002,
  "kg_per_piece_max": 0.02,
  "kg_per_ctn_min": 5,
  "kg_per_ctn_max": 25,
  "qty_per_ctn_min": 100,
  "qty_per_ctn_max": 2000,
  "confidence": 0.82,
  "basis": "小型塑料发饰，按轻小件日用品估算。"
}
```

硬规则：

- 总重量必须闭合。
- 单件重量必须在合理区间内。
- 单箱重量必须在合理区间内。
- 如果总重量闭合会导致任一品类重量不合理，则必须重新选择候选或调整数量，不能只写警告。

### 6. 价格估算

价格模块需要独立成服务，支持多数据源和缓存。

价格源优先级：

1. Amazon Creators API 或可用的 Amazon offer 数据。
2. 其他美国电商公开价格。
3. 批发/跨境平台价格。
4. 客户清单原始单价。
5. 历史同品类价格库。
6. 大模型估算。

Amazon 官方 PA-API 文档显示旧 PA-API 已提示迁移到 Creators API，且旧 `Offers` 资源应改用 `OffersV2`；因此实现上不能把单一 Amazon 接口写死，应采用 provider 抽象。

价格归一化输出：

```json
{
  "query": "plastic hairpin",
  "samples": [
    {
      "source": "amazon",
      "title": "Plastic hair clips set",
      "price_usd": 6.99,
      "pack_qty": 100,
      "unit_price_usd": 0.0699,
      "url": "..."
    }
  ],
  "retail_avg_unit_price": 0.08,
  "declared_unit_price": 0.024,
  "basis": "retail average * 30%",
  "confidence": 0.78
}
```

硬规则：

- 单价不能只为贴近目标税金而压低。
- 总货值必须有最低合理比例，不能出现 3% 级别的极低货值。
- 如果无法联网搜价，必须标记价格置信度，并使用清单价、历史价或 LLM 估算兜底。

### 7. 初稿生成

生成阶段只接收已经通过候选、HS、重量、价格校验的数据。

生成目标：

- 输出行数符合用户要求。
- 覆盖提单品名。
- 优先使用清单归纳品类。
- 总箱数闭合。
- 总重量闭合。
- 单件重量和单箱重量合理。
- 单价有依据。
- 总货值合理。
- 税金接近期望值。

### 8. 硬校验和重试

生成后必须执行硬校验：

- `manifest_origin_ratio`：来自清单归纳池的行数比例。
- `replacement_ratio`：替换清单行数比例。
- `bill_coverage`：提单品名覆盖情况。
- `hs_semantic_match`：HS 与品名语义一致性。
- `weight_plausibility`：单件/单箱重量合理性。
- `price_plausibility`：单价合理性。
- `value_floor`：总货值最低比例。
- `tax_gap`：税金目标误差。
- `quantity_consistency`：数量与箱数、原清单规模是否冲突。

校验失败时，不允许输出，只能回到对应阶段修复。

## 效率设计

为了兼顾严谨性和运行效率，流程应避免逐行调用外部服务。

优化策略：

- 清单归纳只做一次 LLM 批量调用。
- HS 查询按归纳后的候选品类查，不按原始 185 行逐行查。
- 价格搜索只对最终候选品查，不对所有清单品查。
- 重量合理性按候选批量询问 LLM。
- HS 查询、价格查询可以并发执行。
- 外部查询统一缓存：
  - `manifest_summary_cache`
  - `hs_query_cache`
  - `price_query_cache`
  - `weight_plausibility_cache`
- 价格搜索设置超时和样本上限，避免拖慢主流程。
- 缓存命中时不重复联网。

## 模块改造建议

### `engine.py`

需要新增或重写：

- `summarize_manifest_categories()`
- `build_manifest_candidate_pool()`
- `map_bill_products_to_manifest_groups()`
- `select_candidates_from_manifest_first()`
- `validate_replacement_ratio()`
- `validate_hs_semantic_match()`
- `validate_weight_plausibility_hard()`
- `validate_price_and_value_floor()`

重点是移除当前 `qualified_manifest = []` 的跳过逻辑，让归纳后的清单品类成为主候选池。

### `price_client.py`

新增价格服务：

- `PriceProvider`
- `AmazonPriceProvider`
- `GenericWebPriceProvider`
- `HistoryPriceProvider`
- `LLMPriceEstimator`
- `PriceEstimator`

输出统一的 `PriceEvidence` 数据结构。

### `crawler_client.py`

保留 HS 查询职责，不混入价格查询。HS 查询和价格查询应拆开，避免职责膨胀。

### 测试

新增 `CMDUCHN3357475` 回归测试，至少覆盖：

- 输出大部分品名来自清单归纳池。
- 替换清单比例不超过阈值。
- 发夹和钥匙扣数量不能无依据放大到上万。
- 总货值不能低到原始货值的 3%。
- 发夹、钥匙扣单件重量必须合理。
- HS 与爬虫品名不能明显不一致。

## 分阶段落地

### 第一阶段：修正候选来源

- 增加清单归纳。
- 清单归纳池优先。
- 替换清单比例限制。
- 增加 `CMDUCHN3357475` 回归测试。

### 第二阶段：重量硬校验

- 增加候选级重量合理范围。
- 将单件/单箱重量从 warning 改为 hard failure。
- 重量闭合失败时回到候选/数量分配阶段。

### 第三阶段：价格和货值

- 新增价格服务和缓存。
- 引入外部价格证据。
- 增加总货值下限和单价合理性硬校验。

### 第四阶段：审计输出

- 输出内部审计摘要。
- 记录每个品名的来源、替换原因、HS 采用原因、价格证据、重量依据。

## 验收标准

以 `CMDUCHN3357475` 为基准，重构后应满足：

- 输出品名大部分来自清单归纳后的发饰、钥匙扣、塑料饰品等相关品类。
- 替换品不超过约定比例。
- 不再出现电动钻、空气炸锅等与清单主语义无关的补充品。
- 发夹和钥匙扣数量接近清单规模或有明确拆分/归并依据。
- 单件重量、单箱重量全部通过硬校验。
- 总货值不再压到原始货值的 3%。
- 每行都有可审计的 HS、重量和价格依据。
